# Why `pixel_bridge` (Rust `image` crate) and C++ `libpng` disagree on three PNG operations

This document compares how PNG decoding behaves in two stacks:

- **`pixel_bridge`** -- the Rust wrapper in this repo. It decodes PNGs through the
  [`image`](https://crates.io/crates/image) crate's `PngDecoder`, which in turn
  wraps the [`png`](https://crates.io/crates/png) crate. `pixel_bridge` reads the
  raw decoded buffer (`read_u8_slice` / `read_u16_slice`) and performs **no** extra
  pixel conversion of its own (see `pixel_bridge/rust/image.rs`).
- **`libpng`** -- the reference C library, driven through its classic read-transform
  API (`png_set_rgb_to_gray`, `png_set_tRNS_to_alpha`, `png_set_strip_16`,
  `png_set_scale_16`, `png_set_expand_gray_1_2_4_to_8`).

Everything below was measured, not recalled. The exact versions used:

| Component | Version | How obtained |
|-----------|---------|--------------|
| `image` crate | `0.25.10` | the version `pixel_bridge` resolves |
| `png` crate | `0.18.1` | transitive dep of `image 0.25.10` |
| libpng | `1.8.0.git` | built from source (`pnggroup/libpng`) |
| zlib | `1.3.2.1` | built from source (`madler/zlib`) |

Reproduce with `./run_compare.sh` (raw transcript saved in `out/results.txt`).
Fixtures are generated by `rust_tools/src/bin/gen_fixtures.rs` so both decoders
eat **byte-identical** PNG files.

---

## TL;DR

| Operation | Same result? | Root cause of any difference |
|-----------|:---:|------------------------------|
| Color -> grayscale | **No** | Different coefficients, **truncate vs round**, and decisively **sRGB-encoded vs linear-light** weighting. Also `pixel_bridge` never does this at decode time. |
| tRNS -> alpha | **Yes (pixel math identical)** | Both expand a matching sample to alpha `0x00`/`0xFF`. The only difference is *policy*: `image` always expands; libpng only if you opt in. |
| Sub-byte up-scaling (1/2/4 -> 8) | **Yes, bit-exact** | Both scale to full range (`val * 255/maxval` == bit replication). |
| 16-bit -> 8-bit down-scaling | **No** | `pixel_bridge` keeps 16-bit. If you reduce, libpng's `strip_16` (truncate) and `scale_16` (round) disagree with each other, and the `png` crate only offers the truncating variant. |

So two of the four operations actually **agree bit-for-bit**; the real divergence
is grayscale conversion and 16->8 reduction. The sections below give the evidence
and the source-level reason for each.

---

## Operation A: color -> grayscale

### What each stack does

**`image` crate.** There is *no* RGB->gray step in the PNG decode path. A color PNG
decodes to `Rgb8`/`Rgb16` and `pixel_bridge` hands those bytes back untouched. If a
caller wants grayscale they call a downstream API such as `DynamicImage::to_luma8()`.
That path (`cast_in_color_space`, `image/src/images/buffer.rs`) uses **floating-point**
coefficients and **round-to-nearest**:

```
Y = round(0.2126*R + 0.7152*G + 0.0722*B)        // weights the STORED (sRGB-encoded) samples
```

(There is also an *integer* path, `rgb_to_luma` in `color.rs`, used by the
per-pixel `to_luma()` trait: `Y = (2126*R + 7152*G + 722*B) / 10000` with integer
**truncation**. `to_luma8()` does not use it -- worth knowing because the two image
APIs can differ by 1 LSB from each other.)

**libpng** (`png_set_rgb_to_gray`, see `png_do_rgb_to_gray` in `pngrtran.c`). Uses
fixed-point Rec.709-ish coefficients over 32768 with **truncation**, and -- crucially
-- does the weighting in **linear light** whenever gamma is known (e.g. an sRGB or
gAMA chunk is present):

```
Y = (6968*R + 23434*G + 2366*B) >> 15            // no-gamma path, truncation
Y = encode( 0.2126*lin(R) + 0.7152*lin(G) + 0.0722*lin(B) )   // when gamma/sRGB known
```

libpng's own comment: *"In all cases the calculation is to be done in a linear
colorspace."*

### Measured (pixels: red, green, blue, and a mixed tone `(123,200,50)`)

`rgb8.png`, no gamma chunk:

```
image  to_luma8        : 54 182 18 173
libpng rgb_to_gray     : 54 182 18 172
```

`rgb8_srgb.png`, identical pixels but tagged sRGB:

```
image  to_luma8        : 54 182 18 173     <- ignores the transfer function
libpng rgb_to_gray     : 126 219 76 180    <- weights in linear light
```

### Why they differ

1. **Encoded vs linear light (dominant).** On the sRGB image, pure red goes to **54**
   in `image` but **126** in libpng -- more than a 2x gap. libpng linearizes each
   channel, weights, then re-encodes; `image`'s `to_luma8` weights the gamma-encoded
   8-bit values directly. This is not a rounding nit; it is a different color-science
   definition of "luminance". (Note `image`'s output is *unchanged* by the sRGB tag --
   it weighted the encoded samples either way.)
2. **Coefficients + scale.** `2126/7152/722` over 10000 vs `6968/23434/2366` over
   32768. These are both "Rec.709", but the rounded fixed-point constants are not
   identical.
3. **Rounding vs truncation.** `image::to_luma8` rounds (`172.7998 -> 173`); libpng's
   no-gamma path truncates (`-> 172`). This alone gives the +-1 you see on the mixed
   pixel in the no-gamma case.
4. **It is not even part of decoding in `pixel_bridge`.** libpng folds RGB->gray into
   the decode; `pixel_bridge` returns RGB and leaves luma to a separate, differently
   defined call.

## Operation B: tRNS -> alpha

### What each stack does

**`image` crate** sets `png::Transformations::EXPAND` unconditionally
(`image/src/codecs/png.rs:60`). With EXPAND, the `png` crate (`decoder/transform.rs`)
turns a tRNS chunk into a full alpha channel: a sample equal to the tRNS value gets
alpha `0x00`, everything else `0xFF` (`0x0000`/`0xFFFF` for 16-bit). Palette + tRNS is
expanded straight to RGBA8. So `pixel_bridge` **always** surfaces an alpha channel
when tRNS is present.

**libpng** does the same expansion, but only when the caller invokes
`png_set_tRNS_to_alpha()` (`png_do_expand` in `pngrtran.c`, matching `0x00`/`0xFF`).
Without that call you keep `Gray`/`Rgb` plus a separate tRNS chunk to honor yourself.

### Measured (all bit-exact equal)

```
gray8_trns.png   image: 0 255 128 0 200 255 255 255   libpng: 0 255 128 0 200 255 255 255
rgb8_trns.png    image: 255 0 0 255 0 255 0 0 ...      libpng: 255 0 0 255 0 255 0 0 ...
palette_trns.png image: 255 0 0 0  0 255 0 128 ...     libpng: 255 0 0 0  0 255 0 128 ...
gray4_trns.png   image: 0 255 85 0 170 255 255 255     libpng: 0 255 85 0 170 255 255 255
```

`gray4_trns.png` is the interesting one: a 4-bit gray of index `5` is the transparent
value. Both stacks scale the sample to `85` *and* set its alpha to `0`. They agree
because the tRNS match is invariant under the (identical) up-scaling:
`raw_pixel == raw_trns  <=>  scaled_pixel == scaled_trns`.

### Why the *value* is identical but the *behavior* can still surprise you

The per-pixel alpha math is the same. The difference is **policy / API surface**:

- `pixel_bridge` gives you alpha whether you asked or not (EXPAND is hard-coded).
- A libpng program that forgets `png_set_tRNS_to_alpha()` gets no alpha channel and
  must compare against the tRNS chunk itself -- a common source of "transparency was
  ignored" bugs that simply cannot happen through `pixel_bridge`.

So: same numbers, different defaults.

## Operation C1: sub-byte up-scaling (1/2/4-bit -> 8-bit)

### What each stack does

**`png` crate** (`expand_gray_u8`): `scaling_factor = 255 / (2^bd - 1)`, then
`sample * scaling_factor`. For bd in {1,2,4} that factor is exactly {255, 85, 17}, so
the result is exact full-range scaling.

**libpng** (`png_do_expand`): **bit replication**, e.g. 4-bit `v -> (v<<4)|v`, 2-bit
`v -> v*0x55`, 1-bit `v -> v*0xFF`.

Bit replication and `v * 255/maxval` are the *same function* for 1/2/4-bit, so:

### Measured (bit-exact equal)

```
gray1.png  image: 0 255 0 255      libpng: 0 255 0 255
gray2.png  image: 0 85 170 255     libpng: 0 85 170 255
gray4.png  image: 0 85 170 255     libpng: 0 85 170 255
```

### Caveat (historical)

This agreement holds for **modern** libpng's `png_set_expand_gray_1_2_4_to_8`, which
scales to full range. The long-deprecated `png_set_gray_1_2_4_to_8` only left-shifted
(1-bit white -> `0x80`, not `0xFF`) and would *not* match. If you see a mismatch here,
suspect an ancient libpng or a left-shift-only expander.

## Operation C2: 16-bit -> 8-bit down-scaling

This is where the stacks most visibly part ways.

### What each stack does

**`pixel_bridge` / `image`** does **not** reduce. Because EXPAND is set (and `STRIP_16`
is *not*), 16-bit images stay 16-bit (`L16`, `Rgb16`, ...). The comment in
`image/src/codecs/png.rs` is explicit: EXPAND is chosen partly to *disable* the png
crate's 16->8 scaling. `pixel_bridge` then exposes them via `read_u16_slice`.

**libpng** offers two different reductions:

- `png_set_strip_16()` -> `png_do_chop`: **truncate**, keep the high byte (`V >> 8`).
- `png_set_scale_16()` -> `png_do_scale_16_to_8`: **round**, `(V*255)/65535` =
  `round(V/257)`.

The `png` crate, for comparison, only implements the **truncating** `STRIP_16`
(`transform_row_strip16`: `out[i] = row[2*i]`) -- it has no rounding reducer. `image`
just never turns it on.

### Measured (gray16, input values `0 130 200 257 258 32768 65280 65535`)

```
pixel_bridge (keeps 16-bit) : 0 130 200 257 258 32768 65280 65535
libpng --strip16 (truncate) : 0   0   0   1   1   128   255   255
libpng --scale16 (round)    : 0   1   1   1   1   128   254   255
                                  ^   ^                 ^
                                  strip vs scale disagree here
```

Three different answers for the same file:

1. **`pixel_bridge`: full precision.** `200` stays `200`; no information lost.
2. **`strip_16`: biased-low truncation.** `200 (0x00C8) -> 0`, `65280 (0xFF00) -> 255`.
   Drops the low byte; systematically rounds toward zero.
3. **`scale_16`: rounding.** `200 -> 1`, `65280 -> 254`. Matches `(V*255)/65535`.

### Why they differ

- **`pixel_bridge` vs anything 8-bit:** it is a *precision* difference. The Rust stack
  declines to throw away the low byte at all; a typical 8-bit libpng pipeline must.
- **`strip_16` vs `scale_16`:** truncation (`floor(V/256)`) vs rounding to the nearest
  of `V*255/65535`. They diverge by up to 1 LSB across the range and at the extreme
  (`0xFF00`) even in opposite directions (`255` vs `254`).
- **`png` crate vs libpng's recommendation:** if you *do* force the Rust side down to
  8-bit, you get truncation (matching libpng `strip_16`), **not** libpng's recommended
  rounding `scale_16`. So "reduce 16->8 in Rust" and "reduce 16->8 the way libpng's
  docs suggest" are not the same operation.

`rgb16.png` shows the identical pattern per channel:

```
pixel_bridge : 200 130 65280 257 32768 65535
libpng strip : 0   0   255   1   128   255
libpng scale : 1   1   254   1   128   255
```

## Practical guidance

- **Need grayscale that matches a libpng/C pipeline?** Don't expect `to_luma8()` to
  agree. The big gap is linear-light vs encoded weighting; decide which definition you
  want and apply it explicitly (linearize sRGB before weighting if you want libpng's
  numbers).
- **Relying on transparency?** Both produce identical alpha, but only `pixel_bridge`
  does it automatically. Audit any C side for a missing `png_set_tRNS_to_alpha()`.
- **Handling 16-bit images?** `pixel_bridge` preserves them. If you reduce to 8-bit,
  prefer rounding (`scale_16`-style) over truncation, and note the Rust `png` crate's
  built-in reducer truncates.
- **Sub-byte gray** is the one place you can trust bit-for-bit parity (on modern
  libpng).
